# Events – Custom and DOM Events

## 1. Introduction

### What is an Event?
An event is a signal that something has happened in the system. In the context of a web browser, events are fired inside the browser window to notify code of interesting changes that have occurred. These can be user interactions (clicks, key presses) or system occurrences (network responses, timers).

### Event-Driven Programming
Event-driven programming is a paradigm where the flow of the program is determined by events. Instead of executing scripts sequentially from top to bottom, the application waits for events to occur and responds to them using callback functions or event handlers.

### Why Events are Important in LWC
Lightning Web Components (LWC) rely heavily on events to facilitate dynamic, interactive user interfaces. Events are the primary mechanism for:
- Responding to user actions.
- Facilitating decoupled communication between components (Child-to-Parent).
- Updating the UI based on state changes.

### Real-World Use Cases
- A user clicks a **"Submit Claim"** button, triggering a save operation.
- A user selects a **Vehicle** from a list, notifying the parent component to display the Vehicle's service history.
- A search input triggers an event on every keystroke to filter a list of **Dealers**.

---

## 2. What is a DOM Event?

The Document Object Model (DOM) is a programming interface for web documents. It represents the page so that programs can change the document structure, style, and content. 

- **DOM Event**: An action that occurs as a result of user interaction or browser changes applied to DOM elements.
- **Event Source**: The specific HTML element (e.g., `<lightning-button>`) that triggered the event.
- **Event Handler**: The function executed in response to the event.
- **Event Listener**: A mechanism that "listens" or waits for an event to occur on a specific element.
- **Event Object**: A standard JavaScript object containing properties and methods related to the event (e.g., type of event, target element).

### Event Flow Diagram

```text
User Action (Clicks 'Select Dealer' Button)
    ↓
DOM Event (click event generated by browser)
    ↓
Event Handler (handleDealerSelect invoked)
    ↓
JavaScript Logic (Extract Dealer ID, update state)
    ↓
UI Update (LWC engine rerenders component to show Dealer details)
```

## 3. Event-Driven Architecture in LWC

In LWC, the architecture heavily relies on unidirectional data flow (Parent to Child via `@api`) and event-driven upward communication (Child to Parent via Custom Events).

- **User Interaction**: A user types into a VIN (Vehicle Identification Number) field.
- **Event Generation**: The browser creates an `input` event.
- **Event Dispatching**: The input field dispatches the event.
- **Event Propagation**: The event travels through the DOM (bubbling).
- **Event Handling**: A listener on the component catches the event.
- **State Update**: The component's JavaScript updates a reactive property (`this.vin`).
- **Component Rerendering**: The UI reflects the new state.

### Architecture Diagram

```text
[ Parent Component: WarrantyClaimForm ]
   ↑ (Listens for 'claimlinesave' event)
   │
   │ (Dispatches CustomEvent)
[ Child Component: ClaimLineItem ]
   ↑ (Listens for DOM 'click' event)
   │
   │ (User Action)
[ Button: "Save Line Item" ]
```

## 4. Standard DOM Events

LWC leverages standard HTML DOM events. Common events include:

| Event | Trigger Condition | Common LWC Use Case |
|-------|-------------------|---------------------|
| `click` | User clicks an element. | Buttons, links, actionable icons. |
| `change` | Element value changes and loses focus (or selection made). | Dropdowns (`lightning-combobox`), checkboxes. |
| `input` | Value of an `<input>`, `<select>`, or `<textarea>` changes. | Real-time search bars, dynamic form validation. |
| `submit` | A `<form>` is submitted. | Intercepting form submissions in `lightning-record-edit-form`. |
| `focus` | An element receives focus. | Showing help text when clicking into a field. |
| `blur` | An element loses focus. | Validating field input when the user clicks away. |
| `mouseover` / `mouseout` | Mouse cursor hovers over/leaves an element. | Custom tooltips. |
| `keydown` / `keyup` | User presses or releases a keyboard key. | Enter-key submission, custom keyboard navigation. |

    <lightning-input 
        type="search"

    </lightning-input>

## 5. Event Handlers in LWC

Event handlers connect the template markup (HTML) to the component logic (JavaScript).

### Template Event Binding
To bind an event in LWC HTML, prefix the standard event name with `on`.

```html
<lightning-button
    label="Save Claim"
    onclick={handleSave}>
</lightning-button>
```
* **`<lightning-button>`**: Standard LWC base component.
* **`label="Save Claim"`**: Sets the text on the button.
* **`onclick={handleSave}`**: Binds the standard `click` event to the `handleSave` method in JS.

### JavaScript Handler Method
```javascript
handleSave(event) {
    // Prevent default form submission if inside a form
    event.preventDefault();
    
    // Custom logic to save the claim
    this.saveClaimToDatabase();
}
```
* **`handleSave(event)`**: The method invoked. The browser automatically passes the standard DOM `Event` object as the first parameter.

---

## 6. Event Object

When an event fires, it passes an Event object to the handler.

- **`event`**: The core object containing all event metadata.
- **`event.type`**: The name of the event (e.g., `'click'`, `'change'`).
- **`event.target`**: The element that originally dispatched the event.
- **`event.currentTarget`**: The element that the event listener is currently attached to.
- **`event.detail`**: Contains custom payload data (used in LWC base components and custom events).
- **`event.target.value`**: Retrieves the text value from an input element.
- **`event.target.checked`**: Retrieves the boolean state of a checkbox/toggle.

### Comparison Table

| Property | Description | Common Use Case |
|----------|-------------|-----------------|
| `event.target` | The element that originated the event. | Getting the value of an input field (`event.target.value`). |
| `event.currentTarget` | The element handling the event (where the listener is attached). | Used in event delegation to find the parent element that caught the bubbled event. |
| `event.detail` | Custom payload data passed with the event. | Reading the selected row in a `lightning-datatable` or payload from a child component. |

---

## 7. Handling Input Events

Base components often wrap native HTML elements and provide customized event payloads via `event.detail`, or standard access via `event.target`.

### Example: Handling Various Inputs
```javascript
handleChange(event) {
    // Retrieve value from a text/number/combobox input
    this.claimNumber = event.target.value;
}

handleToggle(event) {
    // Retrieve boolean from a checkbox/toggle input
    this.isWarrantyActive = event.target.checked;
}
```
* **`this.claimNumber = event.target.value;`**: Directly reads the user's input from the field that triggered the event and assigns it to a reactive JS property.

## 8. Custom Events

Custom Events are used to communicate from a Child component to a Parent component.

- **What they are**: Developer-defined events based on the native `CustomEvent` interface.
- **Why required**: LWC enforces Shadow DOM and unidirectional data flow. Children cannot mutate parent data directly.
- **When to use**: Whenever a child component needs to notify its parent of a change, action, or request.

### Basic Example
```javascript
// Inside Child Component
const event = new CustomEvent('selected');
this.dispatchEvent(event);
```
* **`new CustomEvent('selected')`**: Creates a new event named 'selected'. Best practice is all lowercase.
* **`this.dispatchEvent(event)`**: Fires the event from the current component, allowing parent elements to listen for `onselected`.

---

## 9. Custom Event with Data

To send data upward, use the `detail` property of the `CustomEvent` configuration object.

### Example
```javascript
// Inside ClaimLineItem component
selectLineItem() {
    this.dispatchEvent(
        new CustomEvent('selected', {
            detail: {
                recordId: this.recordId,
                status: 'Approved'
            }
        })
    );
}
```
* **`new CustomEvent('selected', {...})`**: Defines the event name and an options object.
* **`detail: { recordId: this.recordId }`**: The payload. Wrapping primitive data in an object is highly recommended for future scalability.
* **`this.dispatchEvent(...)`**: Emits the event up the component tree.

## 10. Child-to-Parent Communication

Child-to-Parent communication relies entirely on Custom Events.

### Child: Warranty Claim Line (`claimLine.html` & `claimLine.js`)
```html
<template>
    <div class="line-item">
        <p>Part: {partName}</p>
        <lightning-button label="Select Part" onclick={handleSelect}></lightning-button>
    </div>
</template>
```
```javascript
import { LightningElement, api } from 'lwc';

export default class ClaimLine extends LightningElement {
    @api partName;
    @api partId;

    handleSelect() {
        const selectEvent = new CustomEvent('partselect', {
            detail: { partId: this.partId }
        });
        this.dispatchEvent(selectEvent);
    }
}
```

### Parent: Warranty Claim (`warrantyClaim.html` & `warrantyClaim.js`)
```html
<template>
    <c-claim-line 
        part-name="Engine Block" 
        part-id="PRT-001" 
        onpartselect={handlePartSelection}>
    </c-claim-line>
    <p>Selected Part ID: {selectedPartId}</p>
</template>
```
```javascript
import { LightningElement } from 'lwc';

export default class WarrantyClaim extends LightningElement {
    selectedPartId;

    handlePartSelection(event) {
        // Retrieve data from child event payload
        this.selectedPartId = event.detail.partId;
    }
}
```
* **`onpartselect={handlePartSelection}`**: The parent listens to the child's `partselect` event by prefixing it with `on`.
* **`this.selectedPartId = event.detail.partId;`**: The parent extracts the child's data via `event.detail`.

## 11. Parent-to-Child vs Child-to-Parent Communication

| Feature | Parent → Child | Child → Parent |
|---------|----------------|----------------|
| **Mechanism** | Public Properties (`@api`) & Public Methods. | Custom Events (`CustomEvent`, `dispatchEvent`). |
| **Data Direction** | Downward. | Upward. |
| **Coupling** | Parent dictates child state. | Child decoupled, merely broadcasts state changes. |
| **Use Case** | Parent passes a Record ID or data object to child to render. | Child notifies parent a record was edited or a button was clicked. |
| **Example** | `<c-child record-id={myId}></c-child>` | `<c-child onsave={handleSave}></c-child>` |

## 12. CustomEvent Options

When defining a Custom Event, you can pass an options object.

```javascript
new CustomEvent('statuschange', {
    detail: { status: 'Closed' },
    bubbles: true,
    composed: true,
    cancelable: true
});
```

* **`detail`**: The custom data payload (any data type, though objects are preferred).
* **`bubbles`**: Boolean. If `true`, the event propagates up through the DOM tree. Default is `false`.
* **`composed`**: Boolean. If `true`, the event crosses Shadow DOM boundaries. Default is `false`.
* **`cancelable`**: Boolean. If `true`, allows the event's default action to be prevented via `event.preventDefault()`. Default is `false`.

---

## 13. Event Bubbling

Event bubbling is the phase of event propagation where the event moves from the target element upwards through its ancestors in the DOM tree.

- **Parent elements**: Normal DOM nodes (`<div>`, `<section>`).
- **Parent components**: LWC components containing the child.
- **`bubbles: true`**: Required for an event to move past the component's internal root HTML element up to its shadow host.

### Propagation Diagram
```text
<body>
  └─ <c-parent>                     ← Receives if bubbles: true & composed: true
       └─ #shadow-root
            └─ <div>                ← Receives if bubbles: true
                 └─ <c-child>       ← Dispatches Event
```

---

## 14. Event Capturing

Event capturing is the phase of event propagation where the event travels from the top of the DOM down to the target element.

1. **Capturing Phase**: Top of DOM downwards.
2. **Target Phase**: Arrives at the event source.
3. **Bubbling Phase**: Bubbles back up the DOM.

LWC primarily uses the Bubbling phase. By default, LWC listeners catch events during the bubbling phase. Capturing is rarely used in typical LWC development but is part of standard web specifications.

---

## 15. composed Events

Shadow DOM encapsulates a component's internal DOM. Events do not cross this boundary by default.

- **`composed: true`**: Allows an event to break out of the Shadow DOM boundary and continue propagating through the standard DOM.
- **Relationship**: An event usually needs `bubbles: true, composed: true` to traverse from a deeply nested child all the way up through multiple LWC parents.

**Warning**: Do not automatically use `bubbles: true, composed: true`. It creates "leaky" components. Events should be treated as private API. Only bubble/compose if absolutely necessary (e.g., standardizing global UI events).

---

## 16. Event Retargeting

Because Shadow DOM enforces encapsulation, external components shouldn't know the internal HTML structure of another component.

When an event with `composed: true` crosses a Shadow DOM boundary, the browser **retargets** `event.target`.
- Inside the component, `event.target` is the actual button clicked.
- Outside the component, `event.target` is retargeted to the custom element host (e.g., `<c-child>`).

This protects the component's internal markup from being manipulated by external scripts.

---

## 17. stopPropagation()

`event.stopPropagation()` prevents further propagation of the current event in the capturing and bubbling phases.

- **When to use**: When you have nested clickable elements (e.g., a button inside a clickable row) and you don't want the parent container to trigger its click logic when the child button is clicked.

```javascript
handleRowClick(event) {
    // Handle row selection
}

handleDeleteButtonClick(event) {
    event.stopPropagation(); // Stops the event from bubbling up to the row
    // Handle delete action
}
```

---

## 18. preventDefault()

`event.preventDefault()` cancels the default behavior the browser would normally execute for that event.

- **Default browser behavior**: Clicking an `<a>` tag navigates to a URL. Submitting a `<form>` reloads the page.
- **When to use**: To intercept standard HTML actions and replace them with JavaScript logic (like LWC Apex calls or navigation mixins).

```javascript
handleFormSubmit(event) {
    event.preventDefault(); // Prevents standard page reload
    this.customLwcSaveLogic();
}
```

---

## 19. Event Delegation

Event delegation is a performance optimization technique. Instead of attaching 100 event listeners to 100 rows in a list, you attach **one** listener to the parent container.

### Example
```html
<!-- Parent Container -->
<ul onclick={handleListClick}>
    <template for:each={workOrders} for:item="wo">
        <li key={wo.Id} data-id={wo.Id} class="wo-item">
            {wo.Name}
        </li>
    </template>
</ul>
```
```javascript
handleListClick(event) {
    // Check if the clicked target has the data-id attribute
    const workOrderId = event.target.dataset.id;
    if (workOrderId) {
        this.selectWorkOrder(workOrderId);
    }
}
```
* **`data-*` attributes**: Store data directly on the DOM element.
* **`event.target.dataset`**: Retrieves the stored data attributes.

## 20. Event Naming Conventions

LWC enforces strict rules and best practices for custom event names to align with standard HTML DOM events.

| Practice | Explanation | Example (Good) | Example (Bad) |
|----------|-------------|----------------|---------------|
| **No spaces/dashes** | DOM events don't use them. | `recordselect` | `record-select` / `record_select` |
| **All Lowercase** | HTML attributes are case-insensitive. LWC converts mixed case to lowercase, causing listener mismatches. | `statuschange` | `statusChange` |
| **No "on" prefix** | The listener uses `on`, the event itself shouldn't. | `save` | `onsave` |
| **Meaningful** | Generic names conflict or confuse. | `claimsubmit` | `action` / `click` |

## 21. Event Payload Design

Designing the `event.detail` payload correctly ensures your component remains maintainable and scalable.

### Bad Design (Passing unneeded data / hardcoded primitives):
```javascript
detail: this.recordId 
// Hard to add more data later without breaking parent listeners.
```

### Better Design (Using an Object):
```javascript
detail: {
    recordId: this.record.Id,
    status: this.record.Status
}
// Extensible. You can add 'type' later without breaking existing contracts.
```

**Rules:**
- **Minimal payloads**: Only send what the parent needs. Don't send entire complex Objects/SObjects if an ID suffices.
- **Avoid Mutating**: Never mutate `event.detail` in the parent component.
- **Serializable**: Ensure data in `detail` can be deeply cloned (JSON safe).

## 23. Events with lightning-datatable

The `lightning-datatable` component uses a specific standard event named `rowaction` to handle clicks on buttons or menus inside rows.

### Example
```html
<lightning-datatable
    key-field="id"
    data={invoices}
    columns={columns}
    onrowaction={handleRowAction}>
</lightning-datatable>
```
```javascript
handleRowAction(event) {
    const actionName = event.detail.action.name;
    const row = event.detail.row;

    switch (actionName) {
        case 'view_details':
            this.navigateToInvoice(row.id);
            break;
        case 'delete':
            this.deleteInvoice(row.id);
            break;
        default:
    }
}
```
* **`event.detail.action`**: Contains metadata about the button clicked (e.g., `name`).
* **`event.detail.row`**: Contains the full data object of the row that was interacted with.

## 24. Sibling Component Communication

Siblings (components on the same level) cannot communicate directly via standard events or `@api`.

### Approach 1: Common Parent (Recommended for tightly coupled UI)
```text
Component A (Dispatches Event) → Parent (Listens & Sets Property) → Component B (Receives via @api)
```

### Approach 2: Lightning Message Service (LMS)
For loosely coupled components (e.g., in different regions of a Lightning Page), use LMS. LMS operates over a publish/subscribe model, allowing independent components to communicate without a shared parent. *(Covered deeply in a separate module).*

## 25. Events and Shadow DOM

Shadow DOM encapsulates markup, styles, and events.

### Encapsulation Diagram
```text
[ Parent Component (Shadow Host) ]
      | (Listens to 'update')
  ============================
  Shadow DOM Boundary
  ============================
      |
      [ div ]
         |
         [ Child Component ] --> dispatchEvent(new CustomEvent('update'))
```
Without `bubbles: true`, the event stops at `[ Child Component ]`.
With `bubbles: true` but `composed: false`, it stops at the `Shadow DOM Boundary`.
With `bubbles: true` and `composed: true`, it pierces the boundary and reaches standard DOM ancestors.

## 26. Common Event Problems

| Problem | Cause | Solution | Example |
|---------|-------|----------|---------|
| **Event handler not firing** | Case mismatch in HTML listener. | Use all lowercase for event names. | HTML: `onrecordselect`, JS: `'recordselect'` |
| **`event.detail` is undefined** | Accessing `detail` on a standard DOM event instead of a CustomEvent. | Check if the source is native HTML or an LWC. | `event.target.value` (Native) vs `event.detail.value` (LWC base component) |
| **Event not reaching parent** | Missing `bubbles: true` when dispatched from deeply nested HTML. | Add `bubbles: true` to configuration. | `new CustomEvent('save', {bubbles: true})` |
| **Parent data mutated directly** | Trying to modify an `@api` property directly in child. | Dispatch event to parent; let parent update data. | Dispatch `valuechange`, parent updates state. |

---

## 27. Performance Considerations

- **Event Delegation**: Attach one listener to a list container (`<ul>` or `<tbody>`) rather than listening on 1,000 individual `<button>` elements.
- **Payload Size**: Keep `event.detail` lightweight. Avoid passing huge nested JSON objects. Pass IDs and let the parent retrieve or filter data.
- **Overusing `composed: true`**: Piercing the Shadow DOM repeatedly creates global noise and tight coupling, making components brittle and harder to reuse.
- **Unnecessary Renders**: Dispatching events excessively on `mousemove` or `scroll` can cause UI freezing. Use debouncing techniques for high-frequency events.

## 30. Common Mistakes

- ❌ **Uppercase event names**: HTML is case-insensitive. `this.dispatchEvent(new CustomEvent('myEvent'))` handled by `onmyEvent` usually fails. **Solution**: Use `myevent`.
- ❌ **Forgetting `event.detail`**: Passing primitive data as the second argument `new CustomEvent('save', '123')` is invalid. **Solution**: Pass `{ detail: '123' }`.
- ❌ **Confusing `target` and `currentTarget`**: `target` changes during retargeting across shadow boundaries. **Solution**: Understand component boundaries and use `currentTarget` in delegation.
- ❌ **Using Custom Events instead of `@api`**: A parent component firing an event down to a child is an anti-pattern. **Solution**: Pass data down via `@api` properties or call `@api` methods.

## 31. Best Practices Checklist

- [x] **Use standard DOM events when appropriate**: Rely on standard `click`, `change`, `input` for basic HTML elements.
- [x] **Use CustomEvent for child-to-parent communication**: Maintain loose coupling.
- [x] **Keep custom event names lowercase**: Avoid camelCase to prevent listener mismatches.
- [x] **Keep event payloads small**: Send IDs instead of heavy objects.
- [x] **Use meaningful event.detail structures**: Wrap primitives in an object `{ recordId: '123' }`.
- [x] **Use `@api` for parent-to-child communication**: Adhere to unidirectional data flow.
- [x] **Avoid unnecessary bubbles**: Default to `false` to keep components encapsulated.
- [x] **Avoid unnecessary `composed: true`**: Only pierce the Shadow DOM if absolutely required for global architecture.
- [x] **Use event delegation**: For large lists, put `onclick` on the `<ul>`, not on every `<li>`.
- [x] **Keep event handlers focused**: Event handlers should extract data and pass it to helper methods; they shouldn't contain 100 lines of business logic.

## 32. Interview Questions & Answers

### Beginner Questions
**Q: What is an event in LWC?**
A: An event is a signal indicating an action occurred, such as a user click or input change. It triggers an event handler that updates component logic or state.

**Q: How do you listen to a button click in LWC?**
A: Use the `onclick` attribute in the HTML template bound to a JavaScript method: `<lightning-button onclick={handleClick}></lightning-button>`.

### Intermediate Questions
**Q: What is the difference between `@api` and `CustomEvent`?**
A: `@api` allows data to flow downward (Parent to Child) by exposing public properties. `CustomEvent` allows data to flow upward (Child to Parent) by notifying the parent of actions.

**Q: What is `event.detail`?**
A: It is a standard property of the `CustomEvent` interface used to pass custom payload data from the component dispatching the event to the component handling it.

### Advanced Questions
**Q: Explain event bubbling and event capturing.**
A: Capturing is the phase where the event travels down the DOM tree to the target. Bubbling is when the event travels back up from the target to the root. LWC relies primarily on bubbling.

**Q: What is `stopPropagation()` and `preventDefault()`?**
A: `stopPropagation()` stops an event from continuing to bubble up the DOM. `preventDefault()` stops the browser's default behavior for an event, like form submission or link navigation.

### Architect-Level Questions
**Q: How does Shadow DOM affect event propagation, and what is event retargeting?**
A: Shadow DOM encapsulates components, meaning events fired inside do not cross the boundary to the outside by default. If `composed: true` is used, the event breaks the boundary. When this happens, the browser performs **event retargeting**, changing `event.target` from the internal element (e.g., a button) to the custom element host (`<c-child>`) to protect the internal encapsulation.

**Q: Why is overusing `composed: true` a bad practice in enterprise architectures?**
A: It breaks the encapsulation principle of Web Components, creating tightly coupled, global dependencies. If many components use `composed: true`, the DOM becomes noisy, and parent components might accidentally intercept and process events not meant for them, leading to hard-to-debug side effects.

## 33. Revision Summary

- **DOM Events**: Standard browser actions (`click`, `change`).
- **Event Handlers**: JS methods triggered by HTML `on[event]` attributes.
- **Event Object**: Standard JS object passed to handlers containing `target`, `type`.
- **`event.target`**: The element that triggered the event.
- **`event.currentTarget`**: The element the listener is attached to.
- **`event.detail`**: Custom data payload.
- **CustomEvent**: Interface used for developer-defined events.
- **`dispatchEvent()`**: Method to fire a CustomEvent.
- **Child-to-Parent**: Always via CustomEvent.
- **Parent-to-Child**: Always via `@api`.
- **Event Bubbling**: Event traveling UP the DOM.
- **composed**: Event traversing Shadow DOM boundaries.
- **Event Retargeting**: Browser hiding internal shadow nodes by re-assigning `event.target` to the host component.
- **`stopPropagation()`**: Prevents bubbling.
- **`preventDefault()`**: Stops native browser behavior.
- **Event Delegation**: One listener on a parent handling events for many children.
- **Best Practices**: Lowercase names, small payloads wrapped in objects, strictly guarded encapsulation.
